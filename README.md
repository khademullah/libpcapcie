# libpcapcie

libpcapcie is a lightweight C library for building and analyzing PCIe TLP traffic
with a pluggable backend model. It is designed as a clean, open-source base for
PCIe training, experimentation, prototyping, and hardware validation work.

The project currently focuses on:
- PCIe TLP construction and parsing
- Config-space reads and writes
- Filtering and sniffing hooks
- Backend abstraction for PCI, FPGA, and test platforms

It is intentionally small and readable rather than trying to mimic a full
commercial PCIe exerciser stack.

## Features

- Layered TLP objects for Memory, Configuration, and I/O transactions
- Simple filter/callback sniffing API
- PCIe link-status reporting for max and negotiated speed/width across Gen 1–8
- Backends for dummy, PCI, FPGA, ARM DS, and XGIG-style targets
- Scenario-driven dummy link profiles for compliance testing without hardware
- Structured text, CSV, and JSON reporting for PCIe compliance matrix output
- CMake-based build
- Minimal dependencies with a library + example executables structure

## Current status

This repository is best viewed as a prototype / research framework, not as a
fully compliant commercial PCIe exerciser implementation. It is a strong base for
open-source collaboration, hardware bring-up, and teaching/benchmarking work.

## Project goals

The goal is to create an OSS-friendly PCIe tooling foundation that helps:
- enumerate and validate devices
- craft and replay PCIe config transactions
- test backend integration for different hardware access methods
- provide a clear, extensible structure for contributors

## pcieshark

pcieshark is the project’s trace-analysis and capture-inspection frontend.
It provides the open-source PCIe packet-list and GUI workflow for reviewing
TLP traces generated by libpcapcie.

There are two ways to use it:

- CLI mode for quick parsing and summaries
- GUI mode for interactive trace browsing and filtering

The dedicated pcieshark documentation is here:

- [pcieshark/README.md](pcieshark/README.md)

Example CLI usage:

```bash
./build/pcieshark /tmp/pcie_trace.csv
./build/pcieshark /tmp/pcie_trace.csv --summary
```

Example GUI usage:

```bash
./build/gui/pcieshark
```

## PCI backend notes

The built-in PCI backend reads/writes the Linux sysfs PCI config file:

```text
/sys/bus/pci/devices/<domain:bus:device.function>/config
```

This usually requires:
- root privileges, or
- a device permission configuration that allows access to that sysfs node

If you are using a different device than the default one, set:

```bash
export PCIE_PCI_DEVICE=0000:<bus>:<device>.<func>
```

and identify a device with an Express or PCIe capability before running the example:

```bash
lspci -Dnn | grep -Ei 'Express|PCIe|Bridge'
```

Example output from a non-PCIe VM environment:

```text
0000:00:00.0 Host bridge [0600]: Intel Corporation 440FX - 82441FX PMC [Natoma] [8086:1237] (rev 02)
0000:00:01.0 ISA bridge [0601]: Intel Corporation 82371SB PIIX3 ISA [Natoma/Triton II] [8086:7000]
0000:00:07.0 Bridge [0680]: Intel Corporation 82371AB/EB/MB PIIX4 ACPI [8086:7113] (rev 08)
```

In a real PCIe-capable system, you would select an Express endpoint, not a bridge or virtualized host device.

- `xgig` - XGIG backend placeholder

## Example usage

```c
pcie_ctx_t *ctx = pcie_open("pci");
if (!ctx) {
    fprintf(stderr, "Failed to open backend\n");
    return 1;
}

pcie_tlp_t cfg_rd = pcie_tlp_cfg_read(0x0);
cfg_rd.requester_id = 0x0001;

pcie_send(ctx, &cfg_rd);
pcie_close(ctx);
```

## PCIe link capability checks

The PCI backend can inspect the PCIe capability block and report the current link
status, including maximum and negotiated link speed/width and the corresponding
PCIe generation values from Gen 1 through Gen 8.

```c
pcie_link_status_t status = {0};
if (pcie_get_link_status(ctx, &status) == 0) {
    printf("Max link speed: %s\n",
           pcie_link_speed_name(status.max_link_speed));
    printf("Negotiated generation: %s\n",
           pcie_gen_name(status.negotiated_gen));
}
```

This is a useful starting point for compliance-oriented checks that need to
validate whether a link is operating at a target generation such as Gen 5, 6,
7, or 8.

For a simple compliance check, the library also exposes a pass/fail helper that
compares the negotiated link to a minimum expected generation and lane width:

```c
int pass = 0;
if (pcie_check_link_target(ctx, PCIE_GEN_5, 1, &pass) == 0 && pass) {
    printf("Link meets the minimum Gen 5 x1 requirement\n");
}
```

This is the next layer toward automation of PCIe Gen 5–8 validation workflows.

## Golden AI topology reference

The GUI now defaults to a fixed AI PCIe topology that follows the Zephyr/QEMU
reference layout used for accelerated AI and data-centre emulation:

- 4 root ports: `rp1` to `rp4`
- 4 upstream switches: `switch0_up` to `switch3_up`
- 2 downstream ports per switch: `dp0` and `dp1`
- endpoints including `GPU 1..4`, `NVMe 1..2`, and `SmartNIC` devices
- the CPU complex attached to a single PCIe Bus 00 root domain

This is the default “golden” pattern for AI benchmarking in the GUI, and it is
used as the canonical baseline before introducing custom tuning later.

## Innovative workflow: deterministic dummy profiles

The `dummy` backend is intentionally more than a stub. It can emulate named PCIe
link profiles that are useful for app-level testing and CI validation without
real hardware. This is useful when you want to exercise the same tool chain on a
Gen 5 x1, Gen 6 x4, Gen 7 x8, or Gen 8 x16 scenario before plugging into a real
endpoint.

It also supports a flexible user-defined scenario string for performance and
latency modeling, for example:

```bash
PCIE_DUMMY_SCENARIO='gen8x16,latency=250ns,tps=250000,burst=16,jitter=50ns' ./build/pci_link_status dummy
PCIE_DUMMY_PROFILE=gen5x1 ./build/pci_link_status dummy
PCIE_DUMMY_PROFILE=gen6x4 ./build/pci_link_check dummy 6 4
PCIE_DUMMY_PROFILE=gen8x16 ./build/pci_link_matrix dummy csv
```

Supported custom parameters include:

- `profile=gen8x16`
- `latency=250ns` or `latency_ns=250000`
- `tps=250000` or `tokens_per_second=250000`
- `burst=16` or `burst_size=16`
- `jitter=50ns`
- `drop_rate=0.01`

These values shape the dummy backend's virtual timing model so you can emulate a
realistic PCIe workload profile for bring-up, capacity studies, or synthetic
performance testing.

You can also provide a profile directly to the matrix report app:

```bash
./build/pci_link_matrix dummy gen7x8 json
```

This style of deterministic, profile-driven emulation is one of the practical
innovations that helps this project stay useful for automated bring-up and
compliance-style testing without depending on a specific vendor exerciser stack.

## TLP trace capture

The library now records exchanged TLPs in memory and can export them to a pcap
file for later review or offline analysis. This is useful for debugging link
training, protocol traces, and bring-up sequencing without a proprietary
exercise stack.

```bash
./build/tlp_capture dummy /tmp/pcie_tlps.pcap
hexdump -C /tmp/pcie_tlps.pcap | head
```

The capture records each TLP with the direction, type, requester/completer IDs,
length, address, and payload bytes. The output is stored as a simple pcap-style
stream so it can be inspected with common tooling or post-processed by scripts.

The same capture can also be emitted in CSV form for GUI tooling:

```bash
./build/tlp_capture dummy /tmp/pcie_tlps.csv csv
```

This CSV format is the natural input for a Qt-based trace analyzer, where records
can be filtered, summarized, and visualized in a desktop app.

## Qt-based trace analyzer roadmap

The next practical layer is a desktop UI that loads PCIe trace CSV files, displays
TLPs in a table, filters by direction and type, and summarizes counts, throughput,
and error patterns. This keeps the workflow close to the existing library while
making trace analysis more approachable for hardware validation teams.

A Qt 6 app is a sensible starting point because it is mature, cross-platform, and
works well for table-driven protocol analysis GUIs.

## Open-source product direction

The key differentiation is to position this project as:

- open
- scriptable
- explainable
- hardware-agnostic
- portable across test backends
- easy to automate in CI pipelines
- useful in hardware bring-up and validation flows
- easier to integrate into CI and bring-up flows
- transparent for debugging and root-cause analysis
- friendly to research, training, and benchmarking
- extensible for future PCIe generations and custom compliance rules

That makes it distinct from typical protocol exerciser tooling, which is often closed, GUI-driven, and less suited to automation or embedded bring-up work.

To grow this into a more prominent OSS project, the most valuable next steps are:

1. Add a proper open-source license
2. Document architecture and backend contracts
3. Add automated tests and CI
4. Improve portability for Linux/Windows/VFIO-style access
5. Provide example device enumeration workflows and scripts
6. Publish a clean maintainer and contribution model

This project is already shaped like a solid base for that evolution.
